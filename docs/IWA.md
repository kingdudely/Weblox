# IWA — the whole architecture

The client runs as a Chrome **Isolated Web App**. No Tauri, no UDP helper, no
WebSocket bridge, no extension, no COEP juggling, no pointer-lock shim. JS plus
the patched wasm, and a static file server for dev. The window is the canvas: no
overlay, no status text — progress goes to the console and hard stops raise one
alert.

```
isolated-app://<bundle>
  index.html
  boot.js        loader globals, Trusted Types, audio policy, hard-stop alerts
  abi.js         ring layout, generated by tools/patch.py
  stub.js        worker entry point (workerStubUrl)
  rbx-net.js     roblox.com -> controlled frame; binaries -> direct
  rupp.js        TLV1/TLV2 rewriting
  ring.js        tx/rx rings <-> one UDPSocket
  auth.js        <controlledframe>: login, gamejoin, join script
  app.js         boot order
  engine/        staged: WebClient.wasm, glue + prelude, content tree
```

Measured on Chrome 156 / Linux, place `1818`:

```
tx 7046 datagrams   rx 8708 datagrams   5.2 MB replicated
avatar, decals, textures, CoreGui, tool hotbar all render
audio: contexts running, ScriptProcessor sink running
```

## Why this shape

| Browser rule | Answer |
| --- | --- |
| `SharedArrayBuffer` needs cross-origin isolation | an IWA is cross-origin isolated by definition |
| a page cannot open a UDP socket | `UDPSocket` (Direct Sockets), IWA-only |
| `gamejoin` is origin-locked and the cookie is `HttpOnly` | `<controlledframe>` is a real roblox.com context: the browser sends the cookie, CORS is Roblox's policy |
| script URLs need Trusted Types | one default policy per realm (see below) |

The remaining problem is that the session the server hands out depends on the
client identity that asked for it. That is solved with the frame's
`WebRequest` interceptor, scoped to `gamejoin` alone.

## The entry point — Play opens the app

An installed app is launched by roblox.com itself. The Play button emits the
link the native launcher takes, and the scheme registration hands it to the app:

```
roblox-player:1+launchmode:play+gameinfo:<ticket>
  +placelauncherurl:assetgame.roblox.com/game/PlaceLauncher.ashx?request=RequestGame&…&placeId=1818&isPlayTogetherGame=false
  +launchtime:…+browsertrackerid:…+robloxLocale:en_us+gameLocale:en_us
```

```json
"launch_handler": { "client_mode": "navigate-existing" },
"protocol_handlers": [
  { "protocol": "roblox-player", "url": "/?player=%s" },
  { "protocol": "roblox", "url": "/?deeplink=%s" }
]
```

`launch_handler` is not cosmetic: a running app holds 2 GiB of shared memory, so
a second window fails to allocate. `navigate-existing` reloads the window that is
already open, which is also the right behaviour — the new place replaces the
current session.

The rules are IWA-specific
(`third_party/blink/common/custom_handlers/protocol_handler_utils.cc`):

| Rule | Consequence |
| --- | --- |
| `kIsolatedAppFeatures` allows any dash-separated ASCII-alpha scheme except `http`, `https`, `file`, `ms-settings`, `chrome`, `chrome-extension`, `isolated-app` | `roblox-player` and `roblox` are claimable — a PWA could claim neither |
| exactly one `%s`, and it must be in the query string | `/?player=%s` works; a path placeholder is dropped |
| the handler URL must be `isolated-app://` and inside the manifest scope | `/` |
| an entry repeating an earlier entry's URL is dropped | the two schemes need two distinct URLs |
| `navigator.registerProtocolHandler()` throws inside an IWA | the manifest member is the only path |

The launched link arrives percent-encoded in the named parameter; `app.js` takes
`placeId` (and `gameId`, when the link names a job) out of `placelauncherurl`,
and `gameinfo` as the authentication ticket it is. The query is read raw rather
than through `URLSearchParams`, which would rewrite the link's `+` separators
into spaces.

### The installed form is a signed bundle

`tools/build_bundle.sh` stages the app, bundles all of `iwa/`, and signs it with
the key at `~/.weblox-iwa-key.pem` (generated on first build). The key fixes the
origin — `isolated-app://kfknp…/` for this key. Install the resulting
`build/Weblox.swbn` through `chrome://iwa-dev/` → **Install IWA from Signed Web
Bundle**. Chrome writes its own desktop entry and protocol handlers; the app
runs from the bundle with no server.

There is no project-owned OS handler and no `weblox.desktop`. The wrapper and
the rkhost `/launch` handoff existed only for dev mode; both are gone. If Play
is clicked in the same Chrome profile that has the app installed, Chrome handles
`roblox-player:` internally. Clicking Play from another profile or browser
still falls through to Chrome's own OS entry, where Chrome's `%U` navigation can
show its external-protocol dialog; that path belongs to Chrome, not the app.

Dev mode (`run_iwa.sh` + rkhost) remains for engine iteration, without any
custom handler.

### The bundle, the key, and dev mode

`build_bundle.sh` writes `build/Weblox.swbn` (about 143 MB, the engine tree
included) and prints its origin. The key defaults to
`~/.weblox-iwa-key.pem`; keep it, because re-signing with a new key creates a
different app rather than an update. It is never copied into the repo.

Install the bundle in the profile you browse roblox.com with. Same profile is
what keeps protocol handling inside Chrome; a separate profile still goes
through Chrome's OS entry for Play and can show the dialog.

Dev mode remains available for engine rebuilds:

```sh
CHROME=/usr/bin/chromium WEBLOX_IWA_PROFILE=$HOME/.weblox-iwa ./tools/run_iwa.sh
./tools/run_iwa.sh --stop
```

The profile defaults to `~/.weblox-iwa`. Dev mode serves through rkhost on
`127.0.0.1:8770` and installs a dev-mode app; it does not touch the xdg handler.

Uninstalling the signed app is Chrome's own UI (`chrome://apps` or
`chrome://iwa-dev/`). Remove Chrome's generated entry only if it survives; there
is no `weblox.desktop` to clean up, and the old dev profile stays separate.

### Logs

In dev mode, `rkhost` prints `GET /` and missing engine files to its log
(default `/tmp/opencode/rkhost-iwa.log`). The signed bundle has no server and no
wrapper log; once a game starts, the app's DevTools console is the source. A
Play that never opens the app means Chrome did not hand the scheme to the
installed app (wrong profile or browser).

Installing into the everyday profile works — point `WEBLOX_IWA_PROFILE` at
`~/.config/google-chrome` with Chrome closed — but Roblox then appears in that
profile's app list and Play launches that profile's Chrome.

The catch is timing. The app origin shows up in `Preferences` while the install
is still running, so treating that string as "installed" and closing Chrome
early leaves an app with no desktop entry and no scheme registration — Play
then falls through to whatever else claims `roblox-player:`, which is how a
native launcher ends up opening instead. `run_iwa.sh` therefore waits for the
desktop entry, and on a manifest update for the rewrite of the existing one,
before it closes the installer.

Chrome asks once before handing an external scheme to the OS. In the
same-profile signed install there is no handoff and no prompt; in dev mode or
from another browser, tick "Always allow" once and later Play clicks reuse the
app through `launch_handler`.

The login is the native client's: `gameinfo` is a single-use authentication
ticket minted from the browser's session when Play was clicked. `auth.js` posts
it to `auth.roblox.com/v1/authentication-ticket/redeem` from inside the frame —
the same origin Roblox's CORS policy allows — and the reply sets
`.ROBLOSECURITY` in the frame's jar, so a Play click from a logged-in browser
never shows a login page. The ticket is spent by that call and is never logged
or stored; a reloaded link has nothing left to redeem.

There is no second way in. The app stores no credentials: no cookie capture, no
cookie injection, no login page. A launch without a ticket — the app icon, an
expired link, or a `roblox://` deeplink, which carries no `gameinfo` at all —
shows "Open roblox.com and press Play." instead of starting a frame. The ticket
is stripped from the URL as soon as it is parsed, before the first `await`, so
it never sits in the address or in history while the redeem runs.

The frame is not a home page. It is hidden, because Chrome turns a
`roblox-player:` navigation from inside it into `about:blank`: no OS handoff,
and `loadstart` reports `about:blank` rather than the link. Games therefore
start only from a real browser. Leaving a game is not a window close either:
`WasmPlayer.js` would `window.close()` and then `location.replace("about:blank")`
once `__resolveGameExit` resolves; `boot.js` answers `leave`/`native_exit` on
the app's end screen and never forwards the call, so the window survives and
offers the way out.

## The join, exactly

0. Opened by the Play button (`roblox-player:` → `/?player=…`). In the signed
   install Chrome delivers it directly; in dev mode `run_iwa.sh` only stages,
   serves and installs. A link without a ticket cannot sign in.
   The ticket is stripped immediately, then `app.js` restores
   `/?placeId=<id>` before loading `/engine/WasmPlayer.js` — the loader reads
   that query and calls `set_place_id`; without it the lifecycle exits with
   `[LIFECYCLE] no startup place id`.
1. Frame loads `https://www.roblox.com/home`; its cookie jar is memory-only.
2. `redeemTicket()` posts `gameinfo` to
   `auth.roblox.com/v1/authentication-ticket/redeem`, and the reply signs the
   frame in. This is the only path from the Play button.
3. `whoami()` → `GET https://users.roblox.com/v1/users/authenticated` from inside
   the frame confirms it.
4. `join(placeId)` → `POST https://gamejoin.roblox.com/v1/join-game` with the
   native client's body.
5. **`status: 0` is not an error.** A fresh attempt answers `0` with a
   `"JoinPlace=<id>;"` placeholder and `2` once the job exists. Retry while 0.
6. **Do not use `joinScriptUrl`.** `assetgame.roblox.com/Game/Join.ashx` answers
   `301 -> /request-error?code=404` now, in curl and in the browser. Post the
   join again **with the returned `jobId`** and `joinScript` comes back inline as
   an object, 70 fields, `UdmuxEndpoints` and `NetStackTokenValue` included.
7. `UDPSocket({remoteAddress: UdmuxEndpoints[0].Address, remotePort})`.
8. `ring.start()` points the seam at that socket; `/engine/WasmPlayer.js` loads
   after, so RakNet never wakes up without a destination.
9. The engine asks for a join of its own. That request is **answered from the
   reply above**, never forwarded — see below.

### The engine joins too — answer it, do not forward it

The engine does not accept a join script from the page. Left alone it POSTs
`https://gamejoin.roblox.com/v1/join-game` itself, with the *website* body:

```json
{"placeId": 1818, "gameJoinAttemptId": "0173b730-…"}
```

That shape is refused on any universe whose join is gated. Place `1818`
(Crossroads) answers:

```json
{"status":12,"message":"You are not allowed to play this game. (Playtesters Only)"}
```

even though the same account joins it fine through the native body — the gate
reads the client identity in the request, not the user. `status 12` is easy to
mistake for the user-agent rejection below; it is not one, that header is
already rewritten by the time the engine asks.

So `rbx-net.js` holds the reply the page's own join produced and answers the
engine with it verbatim. `app.js`, right after `auth.join()`:

```js
if (self.__rbxNetSetJoin) self.__rbxNetSetJoin(join.reply);
```

`joinAnswer()` matches only `POST /v1/join-game` **for the same `placeId`**, so a
teleport or a different place falls through to the network untouched. One join,
one ticket, and the engine still drives its own transport.

Two things this settles:

* The join happens once. Roblox's per-user join rate limit stops mattering.
* `status: 30, "Let's check if you can join this game"` is not something the
  plumbing can fix. It is Roblox's account gate (age / identity verification)
  on experiences that require it; the account has to clear it on roblox.com.

### The interceptor

The page's own join is a plain `fetch` from inside the frame, and `gamejoin`
hands out a session shaped for the client that asked: a browser user agent gets
`status: 12, "Unable to join Game 211"`. Same cookie, same body, same request —
only the header differs. So:

```js
frame.request.createWebRequestInterceptor({
  urlPatterns: ["*://gamejoin.roblox.com/*"],
  blocking: true,
  includeHeaders: "all",
}).addEventListener("beforesendheaders", (e) => {
  const h = new Headers(e.headers);
  h.set("User-Agent", "Roblox/WinInet");
  e.setRequestHeaders(h);
});
```

**The scope is not cosmetic.** A custom header on *every* roblox.com URL turns
plain GETs into preflighted requests, and Roblox's CORS configs do not allow the
header — the page starts failing everywhere. One host, one header.

## Direct Sockets, as Chrome 156 actually implements them

The streams come from the **resolved `opened` promise**, not from the socket:

```js
const s = new UDPSocket({ remoteAddress, remotePort });
const { readable, writable, localPort } = await s.opened;   // not s.writable
await writable.getWriter().write({ data: bytes });          // a UDPMessage
```

`socket.writable` is `undefined`; the instance only exposes `opened`, `closed`,
`close`. `read()` yields `{ data, remoteAddress, remotePort }`.

## RUPP, in JS

The engine's RakNet emits correct framing, but three fields are session data only
the join script knows, and the edge silently drops anything that disagrees:

| | field | value |
| --- | --- | --- |
| TLV1 subtype 1 | `NetStackTokenValue` | base64 or 32 hex chars in the join script → 16 bytes |
| TLV1 subtype 2 | the server's token | learned from `Reply2` |
| TLV2, handshake | RCC address + `NetStackPort` | |
| TLV2, established | RCC address + `ServerConnections[0].Port` | |

TLV2's port is **subtype-dependent**: advertising `NetStackPort` after the
handshake black-holes every datagram. `iwa/rupp.js` encodes this; it is a port of
the Rust original, kept as its own file because it is the most fragile piece.

## Networking split

| traffic | path | why |
| --- | --- | --- |
| the page's `gamejoin` | frame + `User-Agent` rewrite | needs the cookie, and a native identity |
| the engine's `gamejoin` | answered locally from the reply above | its website-shaped body is gated per-universe |
| `*.roblox.com` (suffix rule) | frame, `credentials: include` | needs the cookie; Roblox only echoes ACAO for its own origins |
| `clientsettings(cdn).roblox.com` | direct | public, `ACAO: *`, and carries the transport flag |
| `contentdelivery.roblox.com` | direct, `credentials: omit` | signed URLs, `ACAO: *`, multi-MB binaries |
| `*.rbxcdn.com` assets | direct | public, CORS-open |

The rule is the suffix, not a list of hosts. A list is a thing to be wrong about:
every host missing from it reaches the network on its own and dies in a
preflight, which is exactly the console noise a list generates.

### Two traps in the direct path

Both of these cost real debugging time and both are invisible in the console
until you know what to look for.

**1. `ACAO: *` cannot be combined with credentials.** A wildcard is only legal on
an uncredentialed request; the browser rejects the pair with a bare
`TypeError: Failed to fetch`. Every avatar, decal and animation is fetched
through a signed `contentdelivery` URL, so leaving `withCredentials` on makes the
character invisible and fills the log with animation failures that look like
asset problems. Strip credentials on the way out:

```js
const opts = { ...init, credentials: "omit" };
```

`auth.request` also retries with `omit` when a credentialed frame fetch throws,
so a wildcard host that slips through the suffix rule still works.

**2. Never send a multi-MB blob through the frame.** The frame path returns the
body as base64 inside an `executeScript` result. One asset is fine; a few hundred
concurrently is megabytes of string garbage per asset, in two realms, and it can
take a 2 GB wasm heap into an allocation failure. Binaries fetch directly.

## The XHR shim

`WebClient.js` drives assets through `XMLHttpRequest`, not `fetch` — sync reads,
streaming, and `responseType = "arraybuffer"` everywhere. `rbx-net.js` replaces
`XMLHttpRequest`, and for hosts it does not route it proxies to the real one.
Three things that shim has to get right, each of which was a visible bug:

* **`responseType` must be copied onto the real XHR at `send()`.** The engine
  sets it after `open()`. Without the copy every asset arrives as a string and
  nothing decodes: no character, no textures.
* **`responseText` throws once `responseType` is set.** Reading it on a
  readyState sync blows up the whole handler; guard it.
* **`responseURL` must exist as a string.** The engine reads
  `p.responseURL.length` on readyState 2; `undefined.length` throws inside its
  minified state machine and surfaces as `worker sent an error!`.

## Trusted Types

CSP ships `require-trusted-types-for 'script'`, so `script.src`, `new Worker()`,
`importScripts()` and `innerHTML` all reject plain strings.

A policy named **`default`** is applied to every sink automatically, so no call
site — ours or the engine's — has to know about it:

```js
trustedTypes.createPolicy("default", { createScriptURL: u => u, createHTML: h => h });
```

**A policy does not cross realms.** Each of the three places needs its own:
`boot.js` for the page, `tools/worker-prelude.js` for a worker, and `stub.js` for
the `workerStubUrl` realm (which runs before the prelude). Missing one is silent:
`importScripts` throws, `rbx-net.js` never loads in that worker, its requests go
out unauthenticated, and the only symptom is a join or an asset that quietly
fails.

## The settings flag

The engine picks RakNet only if told to. `rbx-net.js` rewrites
`FFlagUseRbxTransportClient3` and `FFlagUseRbxTransportServer` to `"False"` in
the `WebClientApp` settings response. Without that it selects RbxTransport and
never calls `RakPeer::Connect`.

`clientsettings` is fetched direct with `credentials: "omit"` — it is
`ACAO: *`, and routing it through the frame is both pointless and, at boot,
circular.

## Staging and the content mirror

rbxcdn denies directory listing and the web client ships no archive, so "the
whole engine tree" cannot be requested. It is **observed**:

```bash
./tools/mirror_engine.py --capture /tmp/opencode/rkhost-iwa.log   # learn paths
./tools/mirror_engine.py                                          # fetch them
./tools/stage_engine.sh                                           # wasm + glue + abi
```

`tools/engine.paths` is that observed list (87 entries, ~48 MB). `rkhost` logs
`MISSING engine/<path>` for anything the client asks for that is not there —
that line is the signal to re-capture.

Files at the **deployment root** are easy to miss because they are not under
`content/`. `stage_engine.sh` copies them explicitly, and
`audio-processor-fast.js` belongs in that set: without it the engine's audio
worker fails, and the failure surfaces as an unrelated `TypeError` deep inside
`WebClient.js`.

## The dev server

`app/rkhost` is ~180 lines: serve a file, attach headers, done. It exists only
because dev-mode install takes an `http://` URL; the signed bundle does not use
it. There is no proxy, no bridge, no cookie handling, no engine special case.

The app's CSP is now a `<meta http-equiv>` in `index.html`, because a signed
bundle does not need rkhost's headers. Chrome injects COOP/COEP/CORP and
`frame-ancestors 'self'` for an IWA; dev mode still also sends the same policy
from rkhost.

## Permissions policy

An IWA declares capabilities in the manifest's `permissions_policy`, and they are
read **at install time**. Missing entries fail silently at runtime:

```json
"permissions_policy": {
  "cross-origin-isolated": ["self"],
  "direct-sockets": ["self"],
  "controlled-frame": ["self"],
  "fullscreen": ["self"],
  "gamepad": ["self"],
  "screen-wake-lock": ["self"],
  "autoplay": ["self"]
}
```

Without `fullscreen`, the engine's `requestFullscreen()` rejects with
`Disallowed by permissions policy`, which reads like an engine bug. A manifest
change requires a reinstall — `run_iwa.sh` tracks a hash of the manifest and
reinstalls when it moves; source changes are live through the dev proxy.

## Running it

Signed bundle (the installed form):

```bash
./tools/build_bundle.sh
# chrome://iwa-dev/ -> Install IWA from Signed Web Bundle -> build/Weblox.swbn
```

The bundle is self-contained; no server has to be running. Install it in the
profile that presses Play, then open the app from Chrome's launcher.

Dev mode (engine iteration only):

```bash
./tools/run_iwa.sh            # stage, serve, install the dev app
./tools/run_iwa.sh --stop     # stop the detached server
```

The dev-mode app proxies every request to `rkhost` on `127.0.0.1:8770`, so that
server has to be running whenever the dev app is. `run_iwa.sh` starts it
detached and leaves it across Chrome restarts. It opens nothing — a game starts
only from the Play button.

Manual dev install:

```bash
./app/rkhost/target/debug/rkhost --root iwa --port 8770
google-chrome --user-data-dir=~/.weblox-iwa \
  --enable-features=IsolatedWebApps,IsolatedWebAppDevMode \
  --install-isolated-web-app-from-url=http://127.0.0.1:8770/ \
  --no-first-run about:blank
# the assigned origin, then:
grep -o "isolated-app://[a-z0-9]\{40,\}" ~/.weblox-iwa/Default/Preferences
```

The origin id is random per dev install, and `grep` without `\{40,\}` truncates it.

## Audio — do not let the mixer be suspended

Three things stack up here, and the last one is the one that actually mattered.

**1. Chrome will not start an `AudioContext` before the page is interacted with.**
The engine builds its context while booting, so it comes up suspended. Worse, a
context suspended **before its first rendering quantum** is latched: every later
`resume()` rejects with `InvalidStateError`. `boot.js` creates one context inside
the first input to unlock the document, and the engine's context comes up running
from then on.

**2. FMOD's AudioWorklet sink is gated on a resume that never settles**, so that
output path is not used. `start()` is
`mContext.resume().then(() => addModule(...))` and only then builds the node —
while the context is suspended there is no sink at all, and the mix goes nowhere.
The legacy output (`ScriptProcessorNode`) builds its node eagerly at start-up,
independent of the resume, so `boot.js` hides `AudioWorkletNode` before the engine
loads and FMOD takes that path. It mixes on the main thread, which is slower, but
it always has somewhere to write.

**3. The engine parks the mixer with `mixerSuspend()` and never lifts it.**
This is what kept the client silent: every context reported `suspended` and
stayed there even though the document was unlocked — a `ScriptProcessorNode`
whose own context is suspended never calls `onaudioprocess`. FMOD's matching `mixerResume()` on input
does not bring the context back. So `boot.js` makes `suspend()` a no-op on every
context it hands the engine: the sink stays running for the session. Suspension
only saves cycles while nothing is playing; refusing it is what makes the client
audible.

Confirmed by measurement, not by ear: `__audio()` reported
`contexts: running`, `sinks: [{kind: "ScriptProcessorNode", state: "running"}]`.

### Watching it

```js
self.__audio()                 // {contexts:[{state,rate}], sinks:[{kind,state,buffer,channels}]}
await self.__audioPeak(1500)   // {state, peak} — amplitude leaving the first sink
```

Every context `suspended` after a click means the document never unlocked (1).
`sinks: []`
means the engine never built its output. `sinks` present, `peak: 0` and playing
audio means the mixer is being fed nothing — a content problem. Input injected
over CDP never unlocks media, so these are only meaningful in a real session.

### When the client dies: `RBXCRASH: ExplicitTerminate`

The one crash seen in a real session, a minute or two into play:

```
RBXCRASH: ExplicitTerminate
Aborted()
Uncaught RuntimeError: unreachable
    at wasm-function[163109]:0x57116b9
    at Pe (WebClient.js)
    at wi (WebClient.js)
    at wasm-function[163119] ...
    ... down to
    at _as_script_node.onaudioprocess
```

Read it as: the engine called `RBXCRASH(ExplicitTerminate)` from inside the FMOD
mix, reported it (`__resolveGameExit({reason:"crash", errorType:"ExplicitTerminate"})`),
then `abort()` → the bare `unreachable` stub (function 163109). It is a deliberate
engine abort, not a trap out of corrupt state, and **nothing is logged before it**.

Mapping the frames: V8 prints `wasm-function[N]:0xOFFSET`, where the offset is a
module offset and `N` counts imports (273) plus bodies in code-section order.
Walking that gives `FMOD_JS_MixFunction` (126654) → `FMOD::Output::mix` (125626) →
125629 → 125616 → … → the crash reporter. Function 125616 contains the string
`NumFrames must be at least {}` — that is a **log record**, not an assert, and the
branch never runs (no such line is ever printed). Do not chase it.

The only non-engine part of that stack is the sink. With `AudioWorkletNode`
hidden the engine uses its ScriptProcessor output, which calls
`FMOD_JS_MixFunction` on the main thread with a 1024-frame buffer. Whether that is
the trigger is unproven: it is rare (once in ~3 minutes of play, and a 10-minute
idle session is clean), and the worklet sink cannot be substituted — with the
worklet visible the engine selects it, asks for `audio-processor-fast.js`, and
never builds a node, so there is no sink and no audio at all.

`boot.js` wraps `window.__resolveGameExit` on assignment: it logs
`[exit] reason=…` and raises an alert for `reason === "crash"`. That is where the
reason is visible, because the engine only logs an opaque object.

To run the mixer unattended for a repro, launch Chrome with
`--autoplay-policy=no-user-gesture-required`; CDP input never unlocks media, but
this policy does, so `onaudioprocess` runs without a real click.

### The heap is fixed at 2 GiB

`FIntWasmMemoryPages` is 32768 pages and the engine creates the memory without a
growth ceiling, and the ring ABI lives at the top of that address range
(`tools/patch.py`), so the size cannot be trimmed — shrinking it moves the ring
out of bounds (`Invalid atomic access index`). If the allocation fails there is no
client, and the usual cause is a second app window holding the same 2 GiB. That
case now raises an alert instead of a console line.

### Content the client expects but the mirror may not have

`WebClient.metadata.json` registers asset paths the engine then reads through the
VFS. A registered path with no file behind it fails as `Temp read failed` or
`MeshContentProvider ... could not fetch`, which looks like an audio or renderer
bug and is neither. Capture the missing paths and fetch them:

```
./tools/mirror_engine.py --capture /tmp/opencode/rkhost-iwa.log
./tools/mirror_engine.py
```

## The home screen (LuaApp) — why the client has none

The engine does contain the desktop app's home: `LuaAppStarterScript`,
`LuaAppExperienceController`, `AppShell`, `HomePageSdui*`,
`returnToLuaAppRequest`, `UniversalApp.rbxm`. When the client leaves an
experience it has nothing to return to, so the canvas goes to `about:blank`.

It cannot be reached from this build, and the code says so plainly. In the
lifecycle function, the whole start-up is gated on one value:

```wat
i32.const 0x10b8f10            ;; startup place id (i64)
i64.load
i64.const 0
i64.ne
if                             ;; place id set -> build the experience and run it
  ...
else                           ;; no place id
  i32.const 2824533            ;; "[LIFECYCLE] no startup place id; exiting"
  i32.const 0
  call 163158                  ;; log
  call 6                       ;; terminate
  br 4                         ;; leave the app loop
end
```

So the no-place branch is a hard exit, not a home screen; the desktop app's
shell lives in a different bootstrap that this module does not contain. What the
harness *can* do is already done: with no `placeId` the loader still starts the
engine (`Ae(...)` without `set_place_id`), which is why the exit line appears at
all. The JS control surface confirms the limit — `Module` exposes
`set_place_id`, `set_preloaded_flags`, `set_channel`, `resume_audio` and the ring
callbacks, and nothing that starts an app shell.

Two practical routes if this is picked up again:

* **Return to a surface we control.** `__resolveGameExit` hands back
  `{reason: "leave" | "native_exit" | "teleport_failed" | "join_failed"}`.
  `boot.js` now intercepts `leave`/`native_exit`, shows the app's end screen and
  does not forward the call, so WasmPlayer's close-then-`about:blank` branch
  never runs. A `<controlledframe>` home page was tried and cannot work: a
  `roblox-player:` navigation from inside the frame is replaced by `about:blank`
  — measured, there is no OS handoff and `loadstart` reports `about:blank`, not
  the link — so Play always has to come from a real browser.
* **Port the app shell.** It would mean a bootstrap that creates a DataModel from
  `UniversalApp.rbxm` (`rbxasset://models/UniversalApp/UniversalApp.rbxm`, not on
  the public CDN in any path form tried) and starts `LuaAppStarterScript` — engine
  work, not a flag.

### Reading this module

Stock `wabt` (0.1.x, as shipped by distros) rejects the module: the type section
uses `exnref`/typed refs ("expected valid result type (got -0x17)"). Use
`wasm-tools` (Bytecode Alliance) instead:

```
wasm-tools print build/WebClient.patched.wasm | grep -m1 -B120 -A30 "i32.const 2824533"
```

`wasm-tools` is not in the build deps; fetch a release binary, print, grep. The
files it prints are enormous, so always pipe instead of writing a `.wat`.

## Debugging

`--remote-debugging-port=9222`, then attach to the target whose type is **`app`**
— `curl 127.0.0.1:9222/json`. Attaching to the `webview` or `about:blank` target
makes a healthy app look hung.

Two in-page diagnostics, both bounded and cheap:

* `self.__rkRing()` → `{ running, tx, rx, txBytes, rxBytes, localPort }`.
  `tx: 0` with a live socket means the engine never called `Connect`, which is
  almost always a failed `gamejoin`, not a transport problem.
* `self.__rbxNetLog` → the last 300 roblox.com calls with `{url, method, status,
  via}`, where `via` is `page`, `worker` or `direct`. It is how the host split
  was measured and how a missing route gets noticed.

## Known edges

* **Packaging.** The signed bundle is the installed form and bundles the whole
  `engine/` tree (about 143 MB), since `script-src 'self'` means the glue cannot
  come from the CDN at runtime. Rebuild and re-sign it after every engine build.
  Dev mode remains the faster engine-iteration loop.
* **The mirror is a capture, not a manifest.** A screen the capture never visited
  can request a file that is not there. Loud on the server, silent in the client.
* **Weekly engine builds.** Re-run `build_patched.sh` and `stage_engine.sh`;
  `docs/PATCHING.md` covers re-finding the patch sites.
